# Screen spec: the presenter's riders panel

Status: proposed in the pull request for issue #351, for [ADR 0007](../adr/0007-riders-in-a-live-session.md)
sections 3 and 4. It adds the riders to the presenter window ([presenter.md](presenter.md)): how many
are in, who they are, and Remove, Lock and New code. Design system: [system.md](system.md).
Neighbouring specs: [rider.md](rider.md) (what the rider sees, including "removed"),
[room-join.md](room-join.md) (what the room screen shows for a new code). Reference mock-ups and
screenshots: [mockups/](mockups/), files `presenter-riders-*.html` (13 states, generated by
[presenter-riders-pages.js](mockups/presenter-riders-pages.js), styled by
[presenter-riders.css](mockups/presenter-riders.css)) and `presenter-riders-<state>-<w>x<h>.png`.
**Where a mock-up and this text differ, the text wins.**

## Purpose

Give the instructor, **on the second display only**, what they need to manage riders joining a live
class: the **count** of riders in, **their nicknames in the order they joined**, a way to **remove**
one, to **lock** joining, and to **make a new join code**. It is a plain list of names. Nothing
about a rider is shown that the rider did not type to the instructor: no reading, no zone, no
time, no score.

**The presenter window only** (ADR 0007 section 4; ADR 0002). Riders are never on the room
screen, never on the companion page (rule 13), never on the class list, and the list is never
written to disk, the class history or a log. It lives in the app's memory for the session and is
cleared when the session ends. With one display the presenter window lies behind the room window (class-list.md, "Where the room
window goes"): the instructor brings it forward to remove, lock or make a new code, and the room
screen's codes ([room-join.md](room-join.md)) need no panel. A riders control on the room screen's
band would be a sixth control, which the owner's "five" (room-2d.md) does not allow: see "Defaults
and open questions".

## Rules the panel keeps

| Rule | How |
|---|---|
| 6. None of MOWL's look | A **plain list of names**: no grid of rider circles, no bar per rider, no ring, no coloured chip per rider, no avatar. One text row each |
| 7. Colour means the planned zone | White, grey and black only; **no zone colour** on anything about riders (the only zone colours in the window stay the room preview's and the next intervals') |
| 13. Rider data one way | The panel shows the nickname and nothing else of a rider. No number beside a name, **no numbering**, no sorting by anything but the order they joined, no totals but the count, no comparison. Nothing from a rider's phone reaches this panel but `rider_joined` and `rider_left` |
| 14. Join code is a session id only | New code makes another session id; it grants no control |
| 15. No team games | No teams, groups, points, badges or "top" anything. A removed rider is not marked or remembered |

Rows are **not numbered** (a numbered list of names reads as a ranking), carry **no join time** and
are not reorderable. A rider who leaves and comes back (a dropped connection, a reloaded page) is
announced again (`rider_joined`, ADR 0007 section 2) and goes **to the end of the list**.

## Layout

The window is the presenter's: the room preview and the cue on the left, the clock and music
column on the right ([mockups/presenter.html](mockups/presenter.html)), at its two client sizes,
**1000 × 720** (the smallest; the preview drops to 560 px) and **1280 × 800**. Sizes here are in
pixels, not shares of the height: the presenter is read at arm's length (presenter.md).

The panel lives in the **right column** and has two forms. The status lines and a resync notice
(with Undo) are **never covered**.

### Closed: the riders row

```
+-------------------------------+
| Clock and music               |
| Running / Following Spotify   |
| [ Resynced, 30 s back  Undo ] |
| Next song in 1:10 ...         |
| [        Pause   Space      ] |
| [Back 5 s ] [Forward 5 s]     |
| ...                           |
|-------------------------------|
| 12 Riders              [Show list]
+-------------------------------+
```

- One row, the **last thing in the right column** (pinned to its foot), at least **56 px** high,
  ruled off by a 1 px `--stage-line` line. The count first (Big Shoulders 800, 30 px), then
  "Riders" (Atkinson 700, 17 px), then a short state in words when there is one ("Locked", "Full",
  "Reconnecting", Atkinson 400, 15 px, `--light-2`; a longer one goes on a line under the row), then the **Show list**
  button at the right.
- The count is **always visible**, with the list closed. It never says anything about who.
- Nothing above it moves: the status, the notice, the next song and the controls are exactly the
  presenter's.

### Open: the drawer

```
+-------------------------------+
| Clock and music               |   the status stays
| [ Resynced, 30 s back  Undo ] |   and so does the notice
|-------------------------------|
| 8 Riders           [Hide list]|   head
| [Lock joining ] [New code    ]|   two actions with their state
|  Joining is open  Old code .. |
| Remove takes a rider out ...  |   the note (3 lines)
|-------------------------------|
| Anna                [Remove]  |   the list: one row each,
| Bo                  [Remove]  |   in the order they joined,
| Carlos              [Remove]  |   scrolls inside the drawer
| ...                           |
+-------------------------------+
```

**Show list** opens a drawer in the right column's free height: it starts under the status lines
and the notice and runs to the foot, **over the next song and the controls** (the room screen
holds the five controls, the keys of room-2d.md work in this window whether or not the drawer is
open, and **Hide list** brings the controls back). While it is open the notice and the status
stay where they are, so an Undo is never hidden.

| Part | Size | Type and notes |
|---|---|---|
| Head | one row, at least 44 px | Count (Big Shoulders 800, 30 px), "Riders" (Atkinson 700, 17 px), the state word if any, **Hide list** at the right |
| Actions | two buttons, half the width each, 8 px apart, at least 44 px high | **Lock joining** (or **Unlock joining**) and **New code**, each with a second line (Atkinson 400, 14 px, `--light-2`) |
| Note | up to three lines, Atkinson 400, 15 px, `--light-2` | "Remove takes a rider out of the class. A removed rider can scan again until you lock joining or make a new code." (ADR 0007, "Consequences") |
| List | fills the rest; scrolls inside the drawer | Rows at least **52 px** high, ruled by 1 px `--stage-line` lines; the nickname (Atkinson 700, 17 px, up to two lines, `dir=auto`) at the left, **Remove** (at least 44 px high, 92 px wide) at the right |

At **1000 × 720** with a resync notice showing, the drawer has room for **at least 4 rows** with no
scroll (the mock-up shows 5); at 1280 × 800 at least 5. With more riders, or when the notice
takes more room, the list scrolls inside the drawer; the head, the actions and the note never
scroll. The drawer is opened and closed by the instructor only: it never opens by itself, not
when a rider joins either.

### The row

- The nickname is **text only** (`textContent`, never markup), one or two lines. 24 wide capitals
  fit on two lines at the narrowest column (368 px). A nickname is **never cut** (it is the thing
  Remove acts on) and never interpreted: markup shows as typed, and `dir="auto"` stops a
  right-to-left name from moving the Remove button. Two riders with the same nickname are two rows.
- **Remove** is a button with the accessible name "Remove Anna". Its focus ring is the
  presenter's 3 px `--light-1` outline.
- The list is a plain list (`ul`), reached with Tab like every other control; arrow keys do not
  move through it.

## The actions

### Remove

Press **Remove** on a row. **The row asks once**, in place:
"Remove Anna from the class?", **Remove** (white fill, black text: the answer that acts) and
**Keep**. No answer in 5 s, Esc, or a press elsewhere is **Keep**. Remove sends `drop_rider` with
the rider's id; the rider's phone shows "The instructor removed you from this class"
([rider.md](rider.md)); the app gets `rider_left` `dropped` and the row goes. The question exists
because the press is one click on a list that can have 60 names, not because removing is serious:
**a removed rider can scan the code again** until joining is locked or the code is new, and the note
says so beside every Remove.

### Lock joining

One button that **says its state in words**, never colour alone:

| State | Button | State line | Row word |
|---|---|---|---|
| Joining open (`lock_state` `locked` false; a session starts open) | **Lock joining**, second line "Joining is open" | | |
| Joining locked | **Unlock joining**, second line "Joining is locked" | "Joining is locked. Riders already in stay." | "Locked" |

Pressing sends `lock` with `true` or `false`; the button changes when `lock_state` comes back, not
when it is pressed (as the room screen's Start/Pause does), so it never shows a state the server
is not in. A locked class refuses every new join, answers `cannot_join` ([rider.md](rider.md)) and
keeps the riders already in, including one who left and comes back within 5 minutes (ADR 0007
section 3). The lock is for riders only: it does not touch the companion's control. It survives a
new code. **The room screen shows nothing of the lock** (rule 13; [room-join.md](room-join.md)).

### New code

**New code** (second line "Old code stops working") asks once, in the actions' place:

> **Make a new code?**
> The old code and its QR code stop working. Riders already in stay. A control code shown here ends.
> [Make new code] [Cancel]

No answer in 8 s, Esc or a press elsewhere is **Cancel**. **Make new code** sends `new_join_code`
and clears the control code and its QR code shown in this window at once (ADR 0007 section 3: the
control code ended with the old join code, and the host is sent nothing for it). When `join_code`
comes back:

- the drawer shows the new code as text for **10 s**, in the state line: "New code BCDF-GHJK. The
  room screen shows it now.";
- the room screen redraws every code in one frame ([room-join.md](room-join.md), "The new code");
- the old code finds nothing for joins, and for the controller routes of ADR 0005.

At most **10 new codes an hour** per session (ADR 0007 section 3). The window counts its own
requests: after the 10th, **New code** is disabled with the second line "10 an hour, used up" until
an hour has passed since the oldest of them (the server ignores a request beyond the limit and
counts it, so the button must not invite one).

**Disabled** controls have a dashed outline and `--light-2` text (the presenter's convention), never
colour alone.

## Motion and reduced motion

There is none beyond the presenter's: the drawer opens and closes at once, rows come and go at
once, no flash and no slide. A row asking "Remove … ?" and the 10 s new-code line change in place.
Reduced motion changes nothing here, because nothing moves. A rider joining adds a row at the end
without any highlight, sound or scroll: a list that jumps while the instructor is reaching for
Remove would be a hazard.

## Measurable checks

The presenter is read at arm's length, so the room-distance heights do not apply (presenter.md);
measure.js runs on every riders-panel shot at 1000 × 720 and 1280 × 800 with the presenter's
checks: contrast, collisions, hue and motion, plus data-min-cap (a floor in pixels) on every text.

| Check | Requirement |
|---|---|
| P1. Text | Every text at least **11.8 px** cap height (17 px type) for names, counts, buttons and the note's first line, and at least **10.5 px** (15 px type) for the state lines and labels. Counts are 30 px Big Shoulders. Contrast at least **7 : 1** for every text on `--stage`, `--stage-raised` and a white plate; 4.5 : 1 for labels |
| P2. Targets | Every button at least **44 px** high, 8 px apart; a list row at least **52 px** high; the Remove button at least 92 px wide |
| P3. Visible at once | Closed: the count and Show list. Open at 1000 × 720 with a notice: the head, both actions, their state, the note and at least 4 rows |
| P4. Never covered | The status lines and a resync notice are fully visible whether the drawer is open or not |
| P5. No collisions | No two texts overlap; a nickname is never cut (two lines at most, the row grows); nothing wraps beyond its slot |
| P6. Plain list | A `ul` of rows with a name and a button; no numbering, no chip, no circle, no bar, no colour, no per-row figure (rules 6, 7, 13) |
| P7. Hue | White, grey and black only in everything this panel adds (rule 7) |
| P8. No scroll but the list | Nothing scrolls except the list inside the drawer; the window never grows |

**Guards the player issue adds** (ADR 0007 section 6): the rider list reaches the presenter's
channel only, never `room-preload`; the list is never written to disk or the class history; the
`rider_state` builder has no rider input.

## Needs from the desktop shell

A presenter channel for the riders: `rider_joined` and `rider_left` events in, `drop_rider`, `lock`,
`new_join_code` and the 10-an-hour counter out. None of it goes to the room window except the new
join code ([room-join.md](room-join.md)), and none of it to the class history or a log.

## Defaults and open questions

- **The drawer covers the controls while open.** The alternative (a third column) does not fit at
  1000 × 720. Reversible: the presenter's full spec (PL5) may move the panel.
- **Both Remove and New code ask once.** ADR 0007 asks for neither; a click on a list of up to 60
  names, and a change that sends every rider's QR code stale, are the two presses worth a second
  look. Lock does not ask: it changes nothing for riders already in.
- **One display has no riders control on the room screen.** Remove, Lock and New code are reachable
  only through the presenter window, which lies behind the room window on one display. Lock and New
  code matter most for a studio with one screen (a stranger scanning the code from the corridor), so
  this is a **question for the Orchestrator and `docs/owner.md`**: a room-screen control would be a
  sixth band control, which the owner's five do not include. Until it is answered, the safe default
  is this spec as written.
- **The nicknames' order is the order of `rider_joined`**, a returning rider going to the end.
