# Screen spec: the handlebar companion

Status: proposed for PL8, first part (plan section 3, "The handlebar companion"). Design system:
[system.md](system.md). Neighbouring specs: [room-2d.md](room-2d.md) (the same class data and
words), [presenter.md](presenter.md) (wording convention, the resync notice) and
[site.md](site.md) (sign-in, plates and notes). Reference mock-ups and screenshots:
[mockups/](mockups/), files `companion-*.html` (22 states, generated by
[companion-pages.js](mockups/companion-pages.js) from [companion-kit.js](mockups/companion-kit.js),
styled by [companion.css](mockups/companion.css)) and `companion-*-<w>x<h>.png`.

## Purpose

A web page on the instructor's own phone, mounted on the handlebar of the instructor's bike,
metres from the computer that runs the class. It is read in glances mid-ride, at about 60 to
90 cm, with a bouncing view, sweat and sometimes gloves. It does two things and nothing else:

- **Teleprompter.** The coaching cue in large type, the interval now (zone as number, name and
  colour; cadence; position), the time left, the next intervals and the next song change.
- **Remote.** Start, pause and resume, previous and next interval, nudge the clock 5 s back or
  forward, and the one-touch undo of a resync ("Resynced, 30 s back", ADR 0001, timing model
  item 5).

It shows and steers the player. It **never controls a bike or any equipment** (rule 2): no
resistance, speed, incline or brake, no sensor, no Bluetooth. It is nothing to install: a page at
`https://<site>/control`. One phone, one role (controller, ADR 0002 section 8); it shows no rider
data and no rider count (rule 13).

## Getting control (rule 14)

Control needs **the instructor's sign-in** or **a one-time control code shown only in the
presenter window**. A rider's join code alone never gives control (ADR 0002, section 8).

| Way | What the instructor does | What the page sends |
|---|---|---|
| QR code (the usual way) | Scans the QR code in the presenter window: `https://<site>/control#<join code>.<control code>` | `POST /api/live/control` with `session` and `code`, at once; the page shows "Connecting" |
| Typed codes | Types the class code and the control code the presenter window shows as text | The same |
| Sign-in | Signed in on the phone with the account that runs the class; types (or scans) the class code | `POST /api/live/controller` with `session` (the one cookie route) |

- The fragment is read once and removed from the address bar (`history.replaceState`), so the
  code is not left in history or shared by accident. Codes are typed as `XXXX-XXXX`; input ignores
  case, spaces and hyphens (ADR 0002, short codes).
- A failed exchange shows one message, whatever the cause (`invalid_code`, `cannot_control`):
  the page cannot and does not say whether the class exists.
- The controller token lives in `sessionStorage` only and is sent as the WebSocket's first
  message (ADR 0002). It is never in the address, never logged, never shown.
- **For the presenter window (PL5 spec):** besides the QR code it must show both codes as text,
  labelled "Class code" and "Control code", so the typed way works. One display has no presenter
  window and no control code: there the page offers sign-in only.

## Content, in priority order

1. **The cue**, as written in the class (rule 10), up to 120 characters, never cut, never
   scrolled.
2. **The zone**: number, name and colour on the gel, with its targets (%FTP, RPE, %HRmax when the
   class's zone scale has them).
3. **Time left in the interval** (the countdown).
4. **Cadence** (an RPM range, or "On the beat" with the song's BPM under it) and **position**
   ("Seated", "Standing"). Running classes (PL10) show the incline word ("Flat", "Raised") in
   place of position and no cadence.
5. **The next intervals**: zone chip (colour and number), name, length, cadence, position; or
   "End of class".
6. **The next song change**, counted in bars while the change lies in a song with beat anchors
   ("in 37 bars"; "in 3 beats" in its last bar), otherwise in time ("in 1:22"; "in about 1:22"
   while the clock is estimated), and the next song's title.
7. **The music link state** (quiet grey while following, a white plate otherwise) and the class
   time left.
8. **The keys.**
9. **A notice**: the resync with its Undo, in place of the interval keys while it shows.

**Visible at once**, in every connected running state at every supported size: the gel's number
and name, the countdown, cadence and position, the whole cue, Pause (or Resume), the next
interval and the next song change. The one exception is the last fitting step below, reached only
by a cue all in capitals: the next rows and the song row then make room for the cue. Nothing
scrolls. Check K6.

## Layout

All sizes are shares of the viewport (vh, vw), one set per orientation, in
[companion.css](mockups/companion.css): a size is `min(a vh, b vw)` so that it is the same share
of the screen on every phone of that orientation and a narrow phone keeps its line lengths. The
product sets them in `dvh` (the height without the browser's bars) and adds
`env(safe-area-inset-*)` to the padding for notches. The page asks for a screen wake lock while
connected, so the phone does not sleep mid-class; where the browser has none, the code page says
"Set your screen to stay on" (not in the mock-ups).

**Supported sizes**: portrait from 360 × 640 to 430 × 932 and landscape from 640 × 360 to
932 × 430, CSS pixels of the visible page. Every state is checked at 390 × 844 and 844 × 390 (the
reference phone, screenshots kept) and at 360 × 640 and 640 × 360 (the smallest of each
orientation; checked, one kept: [running at 360 × 640](mockups/companion-running-360x640.png)). A
390 × 844 phone in a browser with its bars showing is about 390 × 660, inside the range. Smaller
pages still work but may scroll and are not held to the checks.

### Fitting text

- **Countdown**: `M:SS` below 10 minutes, `MM:SS` to 99:59, `99+` above, digits in fixed cells
  (system.md, Type). One size for every format, sized for `MM:SS`, so it never changes size.
- **Cue**: as for the room screen, up to 60 characters at `--c-text`, longer at `--c-text-min`;
  a word longer than a line breaks rather than being cut.
- **Zone name** on the gel: two lines at `--c-value`; a name that needs more (the mock-ups: over
  24 characters) steps down to `--c-minor`, two lines, then an ellipsis. The presenter shows it
  whole.
- **Next rows**: chip, length, cadence (without "rpm") and position always show; the name takes
  the rest and ends in an ellipsis.
- **Song row**: "Next song", the count, then the title, which ends in an ellipsis.
- **Notice**: the head line on up to three lines; the detail on up to three in portrait, none in
  landscape (the presenter has it).
- **Plates** in the top line say the same words as the room screen's plates and are at most
  about 25 characters ("Not hearing the computer"); on a narrow phone a plate wraps to two lines
  rather than push the class time off the screen.
- **Note** after a press: one line, ending in an ellipsis.

**Fitting steps.** The product measures whether the cue fits its box, and takes these steps in
order until it does; it never cuts the cue and never makes it smaller than `--c-text-min`. The
mock-ups take them by hand.

1. Next rows: three in portrait, then two, then one; three in landscape, then two, then one.
2. *tight*: also the notice's detail line goes, in landscape every target after the first goes,
   and the key hints say "Hold" only (the link plate says when following stops).
3. *tighter* (only a cue all in capitals needs it): the next rows and the song row go, the gel
   keeps its first target.

Worst cases ([worst](mockups/companion-worst.html), [with a notice](mockups/companion-worst-notice.html),
[wide](mockups/companion-worst-wide.html)): an 80-character zone name, three targets, `58:58`,
class time `1:58:58`, "On the beat" at 200 BPM, "Standing", the plate "Not a class song", a
120-character cue of long words, 80-character next names and song title, keys whose presses stop
following (hints shortened by step 2); and a 120-character cue all in capitals. All pass at all four sizes.

## Keys

| Key | Action sent | Guard | Shown when |
|---|---|---|---|
| Start | `start` | **Hold** | Before the start, alone and full width |
| Pause | `pause` | none: one touch, always instant | Running |
| Resume | `resume` | **Hold** | Paused (in Pause's place) |
| Back 5 s, Forward 5 s | `nudge` −5000 or +5000 ms | none (small, and undone by the other) | Running and paused |
| Previous interval, Next interval | `previous_interval`, `next_interval` | **Hold** | Running and paused; Next is disabled on the last interval ("Last interval") and Previous on the first |
| Undo | `undo_resync` with the notice's id | none: one touch (ADR 0001) | Inside the resync notice |

**Touch targets.** Every key and field is at least **64 × 64 CSS px** (about 10 mm on a phone,
for a wet or gloved thumb on a moving bike), with at least **12 px** between two targets.
Portrait keys are at least max(64 px, 8.6 vh) high, landscape max(64 px, 17 vh). Labels say what
the press does, in the presenter's words; a key is never a shape alone.

**Guarded: hold to confirm.** Presses that move the class on (start, resume, skip) fire only
after the thumb has stayed on the key for **0.8 s**. While it is down, the key's outline
thickens, its label reads "Keep holding" and a white bar fills along its foot
([holding](mockups/companion-holding-390x844.png)). Lifting the thumb earlier sends nothing. The
thumb may slide up to 16 px outside the key without cancelling (a bouncing bike); further
cancels. A short tap on a guarded key shows "Hold to skip" (or "Hold to start", "Hold to resume")
in its hint for 2 s. Under each guarded key a hint says "Hold", or "Hold, stops following" when
the press hands the clock over from the music (the presenter's "(stops following)").

**Not guarded.** Pause is never delayed: stopping is always one touch. The nudges are small and
reversible. Undo is one touch by ADR 0001. No key ends the class or the session: that is the
computer's.

**After a press.** The key shows its pressed state until the host answers (`ack`). A done command
shows its result in the next state message and a note in the top line for 3 s, in place of the
link: "Next interval: 5 VO2 max", "Paused", "Back 5 s" ([skipped](mockups/companion-skipped-390x844.png)).
A refused command, or no answer in 3 s, shows the plate "Not done. Check the computer" for 5 s.
A vibration (where the browser offers one, 30 ms) marks a fired hold; it is never the only
feedback.

## Motion and reduced motion

Calm, as the room screen: nothing moves between changes except the countdown's digits. The gel's
colour crosses in `--m-change` (700 ms) at an interval change; plates and the note come and go in
`--m-state` (300 ms). The hold bar fills with the thumb's time on the key; it is feedback, not
decoration. There is no beat dot and no flash on the phone. With `prefers-reduced-motion`: colour
changes are instant, plates appear at once, and the hold bar fills in four steps of 0.2 s; the
words "Keep holding" carry the state either way. No state relies on motion.

## Wording

The presenter's convention ([presenter.md](presenter.md)): sentence case, plain words, one fact a
line, controls say what the press does. Link plates use the room screen's words ("Following
Spotify", "Music paused", "Music not heard", "Not a class song", "Song is in twice", "Manual
clock", "Waiting for the first song", "Press Start"). The phone's own: "Not hearing the computer",
"Connection lost", "Another phone has control", "This phone no longer steers the class", "The
class session has ended", "Resynced, 30 s back" / "Resynced, 1:05 forward", "Hold", "Hold, stops
following", "Keep holding". No exclamation marks, no generated text (rule 10).

## Measurable checks

On the mock-ups, [shoot.js](mockups/shoot.js) and [measure.js](mockups/measure.js) run these on
every companion shot (22 states × 4 sizes) with the checks in
[companion-checks.js](mockups/companion-checks.js); `ONLY=companion node measure.js` runs only
them. PL8's CI runs the same on the real page's screenshots against recorded state messages. Cap
height is the measured height of a capital H in the element's font.

| Check | Requirement |
|---|---|
| K1. Text height | Cap height as a share of the **viewport height**, portrait / landscape, and never under the pixel floor: zone numeral **8.5 % / 15.5 %**, 54 px; countdown **8 % / 13.5 %**, 48 px; values (zone name, cadence, position, a code typed) **3.4 % / 6 %**, 21 px; **cue 2.6 % / 4.5 %, 16.5 px**; a cue over 60 characters **2.1 % / 3.7 %, 13.5 px**; next rows, song row, class time, key labels, notice **1.9 % / 3.4 %**, 12.5 px; labels and hints **1.5 % / 2.7 %**, 10 px. At 75 cm a 16.5 px cap (about 2.7 mm) is about 12 minutes of arc; the countdown's 48 px (about 8 mm) about 37 |
| K2. Contrast | WCAG 2 ratio between the text colour and the worst rendered background pixel in its ink: **at least 7 : 1 for every text**, labels included (a handlebar phone is read under studio light) |
| K3. No collisions | No two texts overlap; nothing wraps beyond its slot (data-lines) or is cut, except a designed ellipsis; nothing is covered by a fill |
| K4. Touch targets | Every key and field at least **64 × 64 CSS px**, at least **12 px** apart |
| K5. Guards | Start, Resume, Previous interval and Next interval carry hold-to-confirm (0.8 s); Pause, the nudges and Undo do not. Every key's action is in the allowlist of "Commands"; none touches equipment (rule 2) |
| K6. One screen | No vertical or sideways scroll; while connected and running, the "visible at once" list above is on screen |
| K7. Zone | The gel and every next chip carry the zone number; the gel and the next rows carry the name. No zone colour without its number |
| K8. Hue | Hue only inside an element that stands for a zone: plates, notes, keys, the hold bar and every state are white, grey or black (rule 7) |
| K9. Motion | With reduced motion, no transition or animation lasts longer than 0; nothing repeats faster than three times a second |
| K10. Coverage and tokens | Every text is inside a checked element; every colour comes from tokens.css; the fonts are the two of system.md, loaded from the page's own files |

## Needs from the live-session state

What the page needs, in the room screen's vocabulary (room-2d.md, ADR 0001, ADR 0003), so the
state message maps onto it directly. The contract (the live-session messages, ADR 0005) decides
the message shapes; these are the fields. Everything is sent by the host and routed to
controllers only; none of it comes from or describes a rider (rule 13).

**Class outline** (once on connect, and again when the class changes):

| Field | Values | Used for |
|---|---|---|
| `class.title` | text, ≤ 80 | Before the start, Class complete |
| `class.length_ms`, `class.sport` | ms; `cycling` or `running` | Class time; position or incline |
| `zones[n]` | per zone number 1–7: `name` (≤ 80), `targets` (`ftp_pct` from–to, `rpe` from–to, `hrmax_pct` from–to, each optional) | Gel, next rows |
| `intervals[i]` | `start_ms`, `length_ms`, `zone`, `cadence` (`{from,to}` or `beat`) or `incline`, `position`, `cue` (≤ 120, may be empty), `test` (FTP test or not), `segment` | The interval now and the next rows; the page picks "now" and "next" by `interval.index` from the state |
| `songs[k]` | `start_ms` (class time), `title` (≤ 80), `bpm`, `has_anchors` | "Next song", "On the beat" BPM |

**Clock state** (on every change and at least once a second):

| Field | Values | Used for |
|---|---|---|
| `clock.state` | `ready`, `running`, `paused`, `holding`, `ended`, `ended_holding` (presenter.md, Clock line) | State choice, the pill, "Until the next song" |
| `clock.class_ms`, `clock.at` | class time, and the host's time it was read | The page runs the countdown between messages and freezes it when not running; it never shows a time older than 3 s as current |
| `interval.index`, `interval.left_ms`, `interval.last` | index into `intervals`; ms; bool | Countdown, "Last interval" |
| `estimated` | bool (coasting or off the list) | "estimated", the dashed countdown, "about" |
| `link.state`, `link.app` | `locked`, `before_first`, `paused`, `coasting`, `off_list`, `ambiguous`, `manual`, `manual_before_start`; the music app's name | Top line and plates |
| `song_change` | `in_ms`; `in_bars` and `in_beats` (only while the change lies in a song with beat anchors and the clock is not estimated); `next_song` (index into `songs`) or `end` | The song row |
| `class.left_ms` | ms (remaining windows plus the expected holds, ADR 0001 item 7) | Top line |
| `controls[]` | per action: `enabled`, `stops_following` (bool), `nudge_ms` | Which keys are live, the "stops following" hints, disabled keys |
| `resync` | null, or `id`, `delta_ms` (signed), `reason` (one of the player's short texts, ≤ 60) | The notice and its Undo; gone when the host withdraws it |

**Answers and endings:**

| Field | Values | Used for |
|---|---|---|
| `ack` | `command_id`, `result` (`done` or `refused`), `reason` | The note after a press, "Not done" |
| Close reason | `replaced`, `dropped`, `signed_out`, `ended`; anything else is "lost" | The losing-control states |
| From the control routes | `invalid_code`, `cannot_control` (one message each way) | Code did not work |

**Commands the page sends** (controller to host, the only ones): `start`, `pause`, `resume`,
`next_interval`, `previous_interval`, `nudge` (`ms`: −5000 or +5000), `undo_resync` (`id`),
each with a `command_id`. Nothing else, and nothing that sets resistance, speed, incline or a
brake (rule 2).

**Never sent to the page:** rider nicknames, presence, counts or readings (rule 13); the host,
device or rider tokens; the join code (the page already has it); song positions or audio.
