# Screen spec: the handlebar companion

Status: proposed for PL8, first part (plan section 3, "The handlebar companion"). Built on the
merged live contract: [ADR 0005](../adr/0005-live-sessions-and-the-handlebar-companion.md) and
[schema/live/v1](../../schema/live/README.md). Design system: [system.md](system.md). Neighbouring
specs: [room-2d.md](room-2d.md) (the class words), [presenter.md](presenter.md) (wording, the
resync announcement) and [site.md](site.md) (sign-in, plates and notes). Reference mock-ups and
screenshots: [mockups/](mockups/), files `companion-*.html` (24 states, generated by
[companion-pages.js](mockups/companion-pages.js) from [companion-kit.js](mockups/companion-kit.js),
styled by [companion.css](mockups/companion.css)) and `companion-*-<w>x<h>.png`.

## Purpose

A web page on the instructor's own phone, mounted on the handlebar of the instructor's bike,
metres from the computer that runs the class. It is read in glances mid-ride, at about 60 to
90 cm, with a bouncing view, sweat and sometimes gloves. It does two things and nothing else:

- **Teleprompter.** The coaching cue in large type, the interval now (zone as number, name and
  colour), the time left, the next intervals and the next song change.
- **Remote.** The contract's six actions and no others: `start`, `pause`, `resume`, `skip`,
  `nudge` (5 s back or forward) and `undo_resync`, the one-touch undo of an announced resync.

It shows and steers the player. It **never controls a bike or any equipment** (rule 2): no
resistance, speed, incline or brake, no sensor, no Bluetooth. It is nothing to install: a page at
`https://<site>/control`. It shows no rider data and no rider count (rule 13). "Previous",
"Follow", "Manual" and picking a song occurrence stay on the presenter (ADR 0005, section 4).

## Getting control (rule 14)

Control needs **the instructor's sign-in** or **a one-time control code shown only in the
presenter window**. A rider's join code alone never gives control (ADR 0005, section 3). One
screen is the default (plan section 3, "One screen first"), so sign-in is the usual way in.

| Way | What the instructor does | What the page sends |
|---|---|---|
| Sign-in (the usual way, one screen) | Signs in on the phone with the account that runs the class and types the class code the room screen shows | `POST /api/live/controller` with `session` |
| `/control#<join code>` | Opens a link or QR code that carries the class code only | Nothing: the page fills the class code and offers sign-in; signed in, it shows "Steer this class" for one tap. The join code alone gives no control |
| QR code (second display only) | Scans the QR code in the presenter window: `https://<site>/control#<join code>.<control code>` | `POST /api/live/control` with `session` and `code`, at once; the page shows "Connecting" |
| Typed control code (second display only) | Types the class code and the control code the presenter window shows as text | The same |

**Requirement:** the control code, and any QR code that carries it (`#<join code>.<control
code>`), is shown only in the presenter window, never on the room screen, in one-screen mode
too. The room screen shows the class code alone.

- The fragment is read once and removed from the address bar at once. Codes are typed as
  `XXXX-XXXX`. The page ignores case, spaces and hyphens and sends the shown form. A code that is
  not 8 letters of the alphabet is caught on the page ("Codes are 8 letters"); it never goes out,
  so `invalid_request` should not come back.
- Refusals: `invalid_code` and `cannot_control` read alike, whatever the cause, and say nothing
  about whether the class exists. `controllers_full` has its own state ("Two phones already").
  `too_many_requests` says "Too many tries. Wait a minute and try again."
- The controller token lives in `sessionStorage` only and is sent in `hello`. It is never in the
  address, never logged, never shown.
- **For the presenter window (PL5 spec):** besides the QR code it must show both codes as text,
  labelled "Class code" and "Control code", so the typed way works. When the app offers no
  control code (one display), the phone uses sign-in.

## Content, in priority order

Everything comes from `companion_state`. The field is named in brackets.

1. **The cue** (`now.cue`), as written in the class (rule 10), up to 120 characters, never cut,
   never scrolled. An empty cue leaves the space empty.
2. **The zone** (`now.zone.number`, `now.zone.name`): number, name and colour on the gel.
3. **Time left in the interval** (`now.remainingMs`): the countdown.
4. **The next song change** (`nextSong`): "Next song", the time to it (`atMs` − `classMs`), the
   title and the artist. "in about 1:22", dimmed, while the clock runs on by itself (`link.state`
   `coasting` or `off_the_list`). With `nextSong` null: "None left".
5. **The next intervals** (`next`, up to 3): zone chip (colour and number), zone name, length
   (`lengthMs`). With `next` empty: "End of class".
6. **The music link** (`link.mode`, `link.state`): quiet grey while following and locked, a white
   plate otherwise. **Class time left** (`classRemainingMs`).
7. **The keys**, from `allowed` and `link.mode`.
8. **A notice** in the skip key's place: the resync announcement with Undo, or a refusal.

**Visible at once**, in every connected running state at every supported size: the gel's number
and name, the countdown, the next song change, the whole cue, Pause (or Resume) and the next
interval. The one exception is the last fitting step below, which only a cue written all in
capitals needs: the next rows then make room for the cue. Nothing scrolls. Check K6.

## Layout

All sizes are shares of the viewport (vh, vw), one set per orientation, in
[companion.css](mockups/companion.css). A size is `min(a vh, b vw)`, so it is the same share of
the screen on every phone of that orientation and a narrow phone keeps its line lengths. The
product sets them in `dvh` (the height without the browser's bars) and adds
`env(safe-area-inset-*)` to the padding for notches. The page asks for a screen wake lock while
connected. Where the browser has none, the code page says "Set your screen to stay on" (not in
the mock-ups).

**Supported sizes**: portrait from 360 × 640 to 430 × 932 and landscape from 640 × 360 to
932 × 430, in CSS pixels of the visible page. Every state is checked at four sizes. Screenshots
are kept at 390 × 844 and 844 × 390, the reference phone. The two smallest sizes, 360 × 640 and
640 × 360, are checked too, and one shot is kept:
[running at 360 × 640](mockups/companion-running-360x640.png). A 390 × 844 phone with the
browser's bars showing is about 390 × 660, inside the range.

min(5.6 vh, 3 vw), labels min(4.4 vh, 2.35 vw). On a handlebar mount landscape is the steadier
way round; both are first-class.

### Fitting text

- **Countdown**: `M:SS` below 10 minutes, `MM:SS` to 99:59, `99+` above, digits in fixed cells
  (system.md, Type). One size for every format, sized for `MM:SS`, so it never changes size.
- **Cue**: as for the room screen, up to 60 characters at `--c-text`, longer at `--c-text-min`;
  a word longer than a line breaks rather than being cut.
- **Zone name** on the gel (`zone.name`, up to 80): two lines at `--c-value`. A name that needs
  more steps down to `--c-minor` (the mock-ups do this over 24 characters): two lines, then an
  ellipsis. The presenter shows it whole.
- **Next rows**: chip and length always show; the name takes the rest and ends in an ellipsis.
- **Song** (`title`, `artist`, up to 200 each): one line each, ending in an ellipsis.
- **Notice**: the head on up to three lines. The detail on up to three in portrait; none in
  landscape, since the presenter has it.
- **Plates** in the top line use the room screen's words and are at most about 25 characters.
  On a narrow phone a plate wraps to two lines rather than push the class time off the screen.
- **Note** after a press: one line, ending in an ellipsis.

**Fitting steps.** The product checks whether the cue fits its box. If not, it takes these
steps in order until it does. It never cuts the cue and never makes it smaller than
`--c-text-min`. The mock-ups take the steps by hand.

1. Next rows: three, then two, then one.
2. *tight*: also the notice's detail line goes.
3. *tighter*, only for a cue written all in capitals: the next rows go.

Worst cases ([worst](mockups/companion-worst.html), [with a notice](mockups/companion-worst-notice.html),
[wide](mockups/companion-worst-wide.html)) use the longest content the schema allows:
- an 80-character zone name;
- `58:58` and a class time of `1:58:58`;
- the plate "Not a class song", with the time estimated;
- a 120-character cue of long words;
- 80-character next names;
- a 200-character song title and artist;
- a 120-character cue written all in capitals.

All pass at all four sizes.

## Keys

| Key | Action sent | Guard | Shown when |
|---|---|---|---|
| Start | `start` | **Hold** | `status` `not_started`, alone and full width |
| Pause | `pause` | none: one touch, always instant | `running` or `holding` |
| Resume | `resume` | **Hold** | `paused` (in Pause's place) |
| Back 5 s, Forward 5 s | `nudge` with `deltaMs` −5000 or +5000 | none (small, and undone by the other) | Always, greyed while `link.mode` is `following` (the contract never allows a nudge while following) |
| Next song / Next interval | `skip` | **Hold** | Always. The label says what skip does now: "Next song" while `link.mode` is `following`, "Next interval" on the manual clock |
| Undo | `undo_resync` | none: one touch (ADR 0001) | Inside the resync notice, while `link.canUndo` |

**Live or greyed.** A key is live when its action is in `allowed`. A greyed key has a dashed
outline and its reason underneath, worked out on the page:
- "Not while following" when `link.mode` is `following`;
- "Last interval" for skip on the manual clock with `next` empty;
- "Not now" otherwise.

A tap on a greyed key sends nothing. Undo shows only while `undo_resync` is in `allowed`.

**Touch targets.** Every key and field is at least **64 × 64 CSS px**, about 10 mm on a phone,
so a wet or gloved thumb on a moving bike can hit it. Two targets are at least **12 px** apart.
Labels say what the press does, in the presenter's words. A key is never a shape alone.

**Guarded: hold to confirm.** Start, resume and skip move the class on. They fire only after the
thumb has stayed on the key for **0.8 s**.
- **While held:** the outline thickens, the label reads "Keep holding" and a white bar fills
  along the key's foot ([holding](mockups/companion-holding-390x844.png)).
- **Early lift:** nothing is sent.
- **Movement:** the thumb may slide up to 16 px outside the key without cancelling, for a
  bouncing bike; further cancels.
- **Short tap:** shows "Hold to skip" (or "Hold to start", "Hold to resume") in the key's hint
  for 2 s.
- **Hint:** every guarded key has "Hold" under its label.

**Not guarded.** Pause is never delayed: stopping is always one touch. The nudges are small and
reversible. Undo is one touch by ADR 0001. No key ends the class or the session: only the
computer does that.

**After a press** (ADR 0005, section 5). Each tap is one `command` with a new `id`, the current
`run` and `basis`, the `seq` of the state on screen.
- **Pending:** the key shows "Sending…" until its `ack` or a later state. The page never resends
  by itself and never queues while not connected.
- **`applied` or `duplicate`:** the new state shows, and the top line has a note for 3 s in the
  link's place, such as "Next interval: 5 VO2 max", "Next song", "Paused" or "Back 5 s"
  ([skipped](mockups/companion-skipped-390x844.png)).
- **`refused`:** a white notice in skip's row for 4 s, with ADR 0005's words:
  - "Not while following the music: use the computer" for `would_stop_following` and
    `not_allowed` ([refused](mockups/companion-refused-390x844.png));
  - "Too late, try again" for `stale`, `stale_run`, `invalid` and `rate`;
  - "Not connected" for `host_away`.
- **No `ack` within 3 s:** the key returns and the notice says "No answer. Check the class."
  An `ack` or a state that arrives later wins: it replaces the notice at once.
- **Vibration:** 30 ms where the browser offers it, to mark a fired hold. It is never the only
  feedback.

## Motion and reduced motion

The phone is calm, like the room screen: between changes, only the countdown's digits move.
- At an interval change, the gel's colour crosses in `--m-change` (700 ms).
- Plates, notes and notices come and go in `--m-state` (300 ms).
- The hold bar fills with the thumb's time on the key. It is feedback, not decoration.
- There is no beat dot and no flash on the phone.

With `prefers-reduced-motion`, colour changes are instant and plates appear at once. The hold bar
fills in four steps of 0.2 s, and the words "Keep holding" carry the state either way. No state
relies on motion.

## Wording

The page follows the presenter's convention ([presenter.md](presenter.md)): sentence case, plain
words, one fact a line, and controls that say what the press does.
- **Link plates:** the room screen's words, in the table above.
- **Phone states:** "Reconnecting", "Computer not connected", "Not connected", "Two phones
  already steer this class", "This phone no longer steers the class", "The class session has
  ended".
- **Announcements:** the page writes them from `kind` and `seconds`, since no free text crosses
  the relay: "Resynced, 30 s back", "Resynced, 1:05 forward", "Following stopped: manual clock".
  Seconds of 60 or more are written as `M:SS`.
- **Refusals:** ADR 0005's words, in the Keys section.
- **Keys:** "Hold", "Keep holding", "Not while following", "Last interval".

No exclamation marks and no generated text (rule 10).

## Measurable checks

On the mock-ups, [shoot.js](mockups/shoot.js) and [measure.js](mockups/measure.js) run these on
every companion shot (24 states at 4 sizes), using the checks in
[companion-checks.js](mockups/companion-checks.js); `ONLY=companion node measure.js` runs only
them. PL8's CI runs the same checks on the real page's screenshots, against recorded
`companion_state` messages. Cap height is the measured height of a capital H in the element's
font.

| Check | Requirement |
|---|---|
| K1. Text height | Cap height as a share of the **viewport height**, portrait / landscape, and never under the pixel floor: zone numeral **8.5 % / 15.5 %**, 54 px; countdown **8 % / 13.5 %**, 48 px; values (zone name, time to the song change, a typed code) **3.4 % / 6 %**, 21 px; **cue 2.6 % / 4.5 %, 16.5 px**; a cue over 60 characters **2.1 % / 3.7 %, 13.5 px**; next rows, song title, class time, key labels, notice **1.9 % / 3.4 %**, 12.5 px; labels and hints **1.5 % / 2.7 %**, 10 px. At 75 cm, a 16.5 px cap (about 2.7 mm) is about 12 minutes of arc and the countdown's 48 px (about 8 mm) about 37 |
| K2. Contrast | WCAG 2 ratio between the text colour and the worst rendered background pixel in its ink: **at least 7 : 1 for every text**, labels included, because a handlebar phone is read under studio light |
| K3. No collisions | No two texts overlap; nothing wraps beyond its slot (data-lines) or is cut, except a designed ellipsis; nothing is covered by a fill |
| K4. Touch targets | Every key and field at least **64 × 64 CSS px**, at least **12 px** apart |
| K5. Actions and guards | Every key's action is one of the contract's six (`start`, `pause`, `resume`, `skip`, `nudge`, `undo_resync`) or a page action that sends no command; a nudge carries exactly ±5000 ms. Start, Resume and skip are held (0.8 s); Pause, the nudges and Undo are not. None touches equipment (rule 2) |
| K6. One screen | No vertical or sideways scroll; while connected and running, the "visible at once" list above is on screen |
| K7. Zone | The gel and every next chip carry the zone number; the gel and the next rows carry the name. No zone colour without its number |
| K8. Hue | Hue only inside an element that stands for a zone. Plates, notes, notices, keys, the hold bar and every state are white, grey or black (rule 7) |
| K9. Motion | With reduced motion, no transition or animation lasts longer than 0; nothing repeats faster than three times a second |
| K10. Coverage and tokens | Every text is inside a checked element; every colour comes from tokens.css; the fonts are the two of system.md, loaded from the page's own files |

## Built on the contract

The page reads only what `schema/live/v1` delivers to a controller: `welcome`, `host_status`,
`companion_state`, `ack` and `ended`. It sends only `hello` and `command`. Every message is
validated with the JSON Schema before use (schema/live/README.md). Nothing about a rider reaches
the page, and it gets no token or code after `hello`. The page needs nothing
beyond the merged contract. Where a field it would like is missing, it shows what the bullets
below say, and "Contract gaps" lists the additions.

- **Countdown between messages:** the page counts down from `now.remainingMs` from the moment
  the state arrived, and only while `status` is `running`. States come at least once a second.
  While connected it runs live for at most 3 s past the last state. After that, and while
  Reconnecting or Computer not connected, it is marked "Not live" (dimmed, dashed) and runs on
  until 10 s after the last state; then it goes and the Not connected view shows no countdown
  (ADR 0005, section 6).
- **Estimated:** derived from `link.state` `coasting` or `off_the_list`.
- **Last interval:** derived from `next` being empty.
- **Song change:** given in time, never in bars.
- **Before the start:** shows the first interval and its cue, not the class title.
- **Music app:** called "the music", never by its name.

## Contract gaps (proposals for a later contract pull request)

None of these is needed for the page to work. Each would add something the instructor would use,

guards' word lists (`equipment-words.txt`: cadence, rpm, incline, target(s); `rider-words.txt`:

contract pull requests. They may land only with every guard list unchanged and without a field
