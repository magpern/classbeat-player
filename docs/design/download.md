# Screen spec: the download page

Status: proposed in the pull request for issue #764 (plan PL7). Design system: [system.md](system.md).
Neighbouring spec: [site.md](site.md) (the same website, header, plates, notes and size
convention; this page follows it). Reference mock-ups and screenshots: [mockups/](mockups/), files
`download-*.html` (4 mock-ups, generated by `mockups/download-pages.js`, styled by `site.css` and
`download.css`) and `download-<state>-<width>.png` at 390 and 1280 px. **Where a mock-up and this
text differ, the text wins.**

## Purpose

A page where anyone (no account, no sign-in) gets the desktop player: the latest release for each
system, with its checksum, and a plain statement of whether the build is signed. It is read on a
laptop or a phone, at arm's length, so it uses the website's convention: sizes in pixels, not
shares of the screen height, and the same tokens. It is a list and nothing more: no marketing, no
screenshots of the product, no counts of downloads, no legal text (the owner's). The product's name
is not set here; the header carries the placeholder "Class player" as on every site page, one string
to replace.

Address: `/download`, public. Whether the header of a signed-in visitor shows the usual links is
for the screens issue; the page itself is the same either way.

## Where the data comes from

**Release data is fixed at build time.** The page makes no call to GitHub or to any other host
when it runs, and tests make no network call. The site's build reads the player release's published
files (`SHA256SUMS` and the release's version, date and notes address; written by
`scripts/release-player-assets.sh`, #760) and writes one JSON file into the site's bundle. The page
reads that file from its own bundle. A new release therefore shows on the page after the site is
rebuilt (open item 2).

| Field | Use |
|---|---|
| `version` | "Version 0.1.0" (the tag `player-v0.1.0` without its prefix) |
| `prerelease` | `true` when the tag has a hyphen part: the word "Pre-release" beside the version |
| `date` | "Released 25 Nov 2026", the release's date, in the site's date style |
| `notes_url` | The release's page on GitHub, the target of "Release notes for 0.1.0" |
| `assets[]` | One per system, in this order: macOS Apple silicon, macOS Intel, Windows 64-bit, Linux 64-bit |
| `assets[].system` | The row's heading |
| `assets[].file` | The file name, shown as text |
| `assets[].url` | The release asset's address, the target of "Download" |
| `assets[].sha256` | The checksum, 64 lowercase hex characters, copied from `SHA256SUMS` |
| `assets[].signed` | `true` or `false`; the file names of today's builds carry `-unsigned` |

**Which release is "the latest".** The highest SemVer among published, non-draft releases; a
stable release wins over any pre-release; with only pre-releases, the highest of those, marked.
The page lists the systems the release has. It never invents a row for a system it lacks and never
falls back to an older release for one (a half release shows what it has, and the notes say the
rest).

## Content, in priority order

1. The heading "Download the player" (the one `h1`).
2. The version, its date and "Pre-release" when it is one.
3. The link "Release notes for 0.1.0".
4. The unsigned notice, when any listed build is unsigned (below, "Signing").
5. One row per system: the system's name, its signing label, the file name, the checksum and the
   "Download" button.
6. "Check a download": one line per system family on how to compare a file with its checksum.

Nothing else. No platform detection: a page that guessed the visitor's system would need a script
to read the browser, would guess wrong on a Mac (it cannot tell Apple silicon from Intel), and
would hide the other rows. All four rows are shown, in a fixed order, the same size.

## Signing

- **Every row carries its own label**, a hollow square and the word "Unsigned" (or a filled circle
  and "Signed"), in a bordered tag beside the system's name. Never colour; the page has none.
- **The notice** is a plate (white, black text, as site.md) above the list whenever at least one
  listed build is unsigned. It is part of the page, so it has no `role="alert"`. Its head says
  "These builds are unsigned" (or "Some builds are unsigned" when the release mixes signed and
  unsigned ones; the unsigned rows are the ones labelled). Under it: "macOS and Windows will warn
  you when you open them." and a second line that is a placeholder, `[Owner wording: how to open
  an unsigned build]` (open item 1). When every build is signed there is no notice and the rows say
  "Signed".
- The page states the fact the release data holds and nothing about what it means for the
  visitor beyond that one sentence. No legal text and no promise of safety.

## Layout at each size

CSS pixels. Under 600 is the phone, 600 to 999 the tablet, 1000 and up the desktop. The page column
is at most 960 px; side padding 16, 24, 32 px; the page never scrolls sideways down to 320 px and
with the browser's text at 200 % (sizes are in `rem` in the product).

| Element | Phone | Tablet and desktop |
|---|---|---|
| Header | The name only | The same |
| Version line | Version, then the date on the same line when it fits | The same |
| Row | Name and tag, file name, checksum label, the checksum wrapping between groups (three to a line at 390 px), then a full-width "Download" button | Name and tag, file name and checksum on the left; "Download" at natural width on the right, centred on the row |
| Checksum | Eight groups of eight characters, wrapping between groups | The same groups in two lines of four |
| Check a download | Term above its line | Terms in a 160 px column, lines beside them |

The checksum is eight groups of eight characters with no whitespace between them in the text, so a
selected and copied checksum is the 64 characters with no spaces. It is plain text, never an
image, and the whole 64 are always shown (never shortened).

## Numbers (criteria)

| Criterion | Value |
|---|---|
| Heading, version line | Cap height at least 21 px for the heading, 17 px for the version (phone) |
| System name | At least 17 px cap height (26 px Big Shoulders) |
| Checksum | 18 px Atkinson, cap height at least 12 px; `--light-1` |
| File name, tag word, "Released" line | At least 16 px |
| Labels ("SHA-256 checksum") | 14 px, `--light-3`, labels only |
| Contrast | At least 7 : 1 for every text (the tokens give 19.1 : 1 for `--light-1`, 10.8 : 1 for `--light-2`, 7.2 : 1 for `--light-3`, on `--stage`; black on the white plate 19.1 : 1) |
| Touch targets | "Download" and the release-notes link at least 44 px high; "Download" 48 px |
| Visible at once, 390 × 844 | The heading, the version line, the release-notes link, the whole unsigned notice, and the first row's name, tag and "Download" (as built in the mock-up: the first button ends at y = 676) |
| Visible at once, 1280 × 800 | All of the above and the first two rows complete with their checksums |

No hue anywhere (S4 of site.md); the page uses tokens only and no font is fetched.

## States

| State | When | What it shows |
|---|---|---|
| **Loading** | From the first paint until the release data has been read | The heading; the line "Looking for the latest release" with a hollow circle (`role="status"`); the four systems' rows with their names and the word "Loading" in place of the tag, file, checksum and button. The system names are fixed in the page, so the rows keep their height and nothing jumps when the data arrives. No spinner animation |
| **Latest found** | The data holds a release with at least one asset | Everything under "Content" above |
| **No release yet** | The data holds no release (nothing published, or only drafts) | The heading and a note (outlined, `role="status"`): "No release yet" and "No version of the player has been published. It will be listed here when there is one." No list, no notice, no button, no empty rows |
| Could not read the list (a fourth state, beyond the three the issue names) | The release data is missing or does not parse | The heading and a plate (`role="alert"`): "The list of releases could not be read", "Reload the page. If it happens again, the page is at fault, not your computer.", and a "Reload" button |

Loading is brief by design (the data is in the bundle), but it is a real state: the page is
shown before its code has read the data, and a test holds it there. The loading state needs no
script to look right. When scripting is off the page says so in one line (a `noscript` plate:
"This page needs scripting to show the list of releases.", placed in place of the loading line).

The fixed words: "Download", "Release notes for
&lt;version&gt;", "SHA-256 checksum", "Unsigned", "Signed", "Pre-release", "Released &lt;date&gt;".

## Motion

None. The loading state does not animate (no spinner, no shimmer); the hollow circle is static.
Replacing the loading rows with the list is a single repaint. Nothing changes under
`prefers-reduced-motion`, because there is nothing to reduce. Focus rings are 3 px `--light-1`
with 3 px offset (site.css) and are not animated.

## Accessibility

- One `h1`; each row is a `section` named by its system heading; "Download" has the accessible
  name "Download for macOS, Apple silicon" (the visible word is "Download"; this satisfies label in
  name).
- The tag is text, so it is read with the row. The notice is a `section` named by its head.
- A skip link first, as every site page. Links and buttons are real elements in tab order:
  release notes, then each "Download".

## Open items

1. **Owner wording:** the "how to open an unsigned build" line in the notice is a placeholder; the
   steps differ per system and may need the owner's wording (docs/owner.md). Until it is set, the
   placeholder is not shown in the product: the notice shows its first sentence only.
2. **When the page updates.** The data is read at build, so the site is rebuilt on every player
   release (the release runbook, #763, owns that step). Until it does, the page is behind by one
   release at most.
3. **The Windows row** is a `.tar.gz` today, like the others (#760). If a later release ships an
   installer, only the data changes.
4. **The product name** in the header and heading ("the player") is the placeholder of site.md.

## What the page never shows (plan section 3)

The page names no music source, shows no class, rider, sensor or scene, has no hue and no
imagery, and gives no legal or safety assurance. It touches none of rules 1 to 15; it is the plain
list of a file and its checksum. It links only to the release's own page and its own files on
GitHub, as ordinary links the visitor follows; the page itself loads nothing from there.
