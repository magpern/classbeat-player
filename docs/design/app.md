## Purpose

The app is one install with two modes (ADR 0011 section 1). In **rider mode** it is the rider page
of [rider.md](rider.md), bundled, with a class code field because nobody opens the app from the QR
code's address. In **instructor mode** it is the player: the class list
([class-list.md](class-list.md), laid out for the phone) and the class screen of
[play.md](play.md), plus what only the app has: pairing, the screen-lock gate, following Spotify
and an external display. This spec covers those additions. Everything else is the rider page's or
`/play`'s and keeps their specs.

The direction: **the app reads as the rider page and `/play` read**. No new type, no new colour, no
new key shape, no splash or illustration. The same black stage, the same two fonts, the same white
keys and white plates. The one new element is the **mode tag** at the top of every page outside a
class, which says in words which mode the app is in, because the two modes look alike on purpose
and must never be confused.

## Who draws what

| Layer | Screens | Why |
|---|---|---|
| **Native** (Kotlin, Android views) | The no-lock screen, the switch question and the switching screen, every pairing screen, the follow sheet | They hold or guard a secret or a mode (ADR 0011 sections 1, 5), or they open a system setting; the web view cannot select or unlock a mode |
| **System** (Android's own UI, not drawn by us) | The screen-lock prompt (`BiometricPrompt` with the device credential), the Custom Tab or browser for the approval, Notification access and App info | We never imitate a system prompt; our screen says what comes next before it opens |
| **Web view** (the bundled page) | Rider mode's pages, the class list, the class screen and the external display's room view | One web code base (ADR 0011 section 1) |

Native screens use the same tokens ([tokens.css](mockups/tokens.css) values exported to Android
resources), the same two bundled fonts and the same sizes in `vh` and `vw` of the window as the
mock-ups, so a native screen and a web page next to it cannot be told apart. The mock-ups mark a
native page with `data-layer="native"`; nothing on the screen shows it.

## Sizes

Every page state is checked at six window sizes; the class screen keeps `/play`'s; the external
display keeps the room's.

| Size | What | Kept as a screenshot |
|---|---|---|
| 390 × 844, 844 × 390 | The reference phone, each way up | Every state |
| 360 × 640, 640 × 360 | The smallest supported phone, each way up | Checked only |
| 768 × 1024, 1024 × 768 | A tablet, each way up | Checked only |
| 1920 × 1080, 1280 × 720 | The external display (app-room-display.md) | Every display state |

A **form** (a page with a text field, when the keyboard is up) may scroll down and is checked in
portrait only, as on the rider page; every other page fits one screen with no scroll. Layout per
orientation is the companion's ([companion.md](companion.md), "Pages"): in portrait one column,
the explanation first and the keys at the bottom; in landscape two columns, the explanation at the
left and the keys at the right. On a tablet held sideways (aspect 8 : 5 or squarer) the text sizes
are set by the height alone, since the companion's width caps are for a 2 : 1 phone.

Window insets: the pages sit inside Android's system bars and the display cutout
(`WindowInsets`); the sizes above are the window inside them.

## Measurable checks

[shoot.js](mockups/shoot.js) and [measure.js](mockups/measure.js) run these on every app shot with
[app-checks.js](mockups/app-checks.js); `ONLY='^app-' node shoot.js` runs only them. The app's CI
runs the same checks on screenshots of the real screens (instrumented tests for the native
screens, the web view's pages as on the rider page), and every floored text stays at least 5 % over
its floor there.

| Check | Requirement |
|---|---|
| A1. Text height, pages | Cap height as a share of the **window height**, portrait / landscape, never under the pixel floor (companion.md K1): values (titles, the pairing code, a typed value) **3.4 % / 6 %**, 21 px; text **2.6 % / 4.5 %**, 16.5 px; key words, plates, steps, status lines **1.9 % / 3.4 %**, 12.5 px; labels, hints, the mode tag **1.5 % / 2.7 %**, 10 px |
| A2. Text height, the class screen | `/play`'s tiers on the phone (play.md, "Measurable checks"), and the room's on a tablet held sideways |
| A3. Text height, the external display | The room's tiers (room-2d.md, C1): every number and cue readable at room distance, with the room's **5 %** safe area |
| A4. Contrast | At least **7 : 1** for every text, labels included, against the worst background pixel of its ink |
| A5. No collisions | No two texts overlap; nothing wraps beyond its slot |
| A6. Touch targets | Every key, switch, field and class row at least **64 × 64 CSS px** (dp on Android), at least **12 px** apart |
| A7. Actions | Every `data-action` is one of the app's own (app-checks.js lists them); none sets resistance, speed, incline or a brake (rule 2); no key's word mentions scanning, a camera or a QR code (rule 12) |
| A8. One screen | No sideways scroll anywhere; every page that is not a form fits with no vertical scroll and has every control inside the window |
| A9. Mode | The mode strip shows on a mode's start page only, never with a class open or a rider joined; every page outside a class carries the mode tag |
| A10. Visible at once, the class screen | play.md's list (the gel's number and name, the link slot, the countdown, the metrics, the cue, the next row, and the band or the score), plus **Follow the music** when it is offered |
| A11. Zone | The zone is always its number and its name as well as its colour, wherever it shows; nothing else carries a hue (rule 7) |
| A12. No other rider | No canvas, picture, ring, count, ranking, team or list of riders on any app screen (rules 13, 15) |
| A13. Motion | Native transitions at most 300 ms, a fade or a slide of the whole page; with Android's "Remove animations" (or reduced motion in the web view) none at all; nothing repeats faster than three times a second |
| A14. No text in a picture | Every word on every screen is live text in the bundled fonts; the app icon and the splash carry no words |

## Motion and reduced motion (all app screens)

- Page to page: the system's default fade, at most 300 ms. A native screen over the web view
  (a sheet, a question) fades in over 200 ms; nothing slides from an edge.
- The "working" marker (a hollow circle) does not spin: it is still, and the words say what is
  happening. Nothing on these screens moves on its own except the code's countdown, which changes
  once a second.
- With Android's "Remove animations" (`ANIMATOR_DURATION_SCALE` 0) or `prefers-reduced-motion`
  in the web view: no transition at all; pages swap at once.
- The class screen's own motion is `/play`'s (play.md, "Motion and reduced motion").

## The room screen on the phone (issue #871, as built in #880)

In instructor mode, opening a class from the list runs it on the phone as the room screen
(`/room.html`'s page, bundled); the external display stays on its idle stage
([app-room-display.md](app-room-display.md)).

- **Portrait, 390 × 844:** the room screen follows [play.md](play.md)'s "Portrait": play's portrait
  grid (the gel and the metrics side by side, then the countdown, the cue and the next row), play's
  tokens, and the score scaled to three minutes. The band sits over the score's box, with keys
  64 px high. The End question is on its own line above its two keys: **End class** at the left,
  **Keep going** at the right, as play.md's "End and its guard".
- **Landscape, 844 × 390:** the desktop room layout, unchanged (room-2d.md).
- Text tiers, contrast and the zone as a number and a name are play.md's and the room's; nothing
  here relaxes them.

## What the app never shows or does (plan section 3)

| Rule | How the app's own screens keep it |
|---|---|
| 2. Software only | No key sets resistance, speed, incline or a brake (A7) |
| 7. Colour means the planned zone | Hue only on the zone's gel and chips on the class screen; every app page, plate, key and note is white, grey and black (A11) |
| 12. No camera | No camera permission, no QR scanning, no key that names one; the class code is typed (A7) |
| 13. Rider data one way | Rider mode shows no other rider, count or list (A12); switching to rider mode drops all instructor state before the rider page loads (app-modes.md); the external display never shows the riders' list (app-room-display.md) |
| 14. Join code is a session id only | The class code field takes the code and nothing else; the app keeps no rider token after leaving |
| 15. No team games | No teams, points, badges or streaks anywhere |

## Open questions

- **Opening the app from the join QR code or a link** (Android App Links): not designed, so the
  rider always types the code. Default: no; the camera app opens the web rider page instead.
- **The restricted-setting step** (app-follow.md): Android 13 and later block Notification access
  for an app installed outside a store until "Allow restricted settings" is chosen in App info. The
  words follow stock Android; the owner's phone may name the menu differently.
- **Follow the music on the class list** as well as on the class screen: default no, so the
  question comes when it matters, with a class open.
